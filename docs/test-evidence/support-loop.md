## DESIGN

1. **Layout.** Everything new of the peer's lives in `peer-side\` so the existing INSTALL step 6 copy (`messenger\*` -> `%USERPROFILE%\ai-courier`, "Root") installs it with no new paste: `doctor.ps1`, `update.ps1`, `CHANGELOG.md`, `allowed_signers` + `BASELINE.json` (both written by `make-release.ps1`, so the first zip needs one owner release run), `support\INDEX.md`, `support\routes\<id>.md`, `support\TICKET-TEMPLATE.md`. Their: `host-side\make-release.ps1`, `host-side\TRIAGE.md`. `messenger-lib.ps1` is NOT edited (both copies stay byte-identical).
2. **Baseline.** Two groups: `root` (every shipped `messenger\` file except `_HOW-TO-DRAFT.md`) and `work` (what kit `setup.ps1` puts in `work\`: AGENTS/CLAUDE/WORKFLOWS/SEATS/.gitignore, `skills\**`, `opencode.json`, `.opencode\commands\*`, plus `outbox-staging\_HOW-TO-DRAFT.md`). `work` = parent of `settings.json staging_dir`. Each file: short id (`r01`, `w07`), group, path, SHA-256. `messenger.md` is hashed with its `model:` line normalized to the template placeholder (setup fills the peer's model in; update keeps it). Plus `version` (integer, only goes up), date, `opencode_version`, `model`, `changelog`, `zip_sha256`.
3. **Doctor** (read-only, safe for the peer's AI to run): changed / missing / added (added = untracked files in Root minus runtime files, and under `work\skills`, `work\.opencode`), version drift, watcher process running, canary pin matches, inbox folder present, key present, last 5 `seen.jsonl` rows (the only watcher log that exists; ids cut to 8 chars, no text). **File ids, not paths**, and no `model:`-style words, so a ticket carries no path/code/AI-address shapes and can come out `NO RED FLAGS: YES` on the host side.
4. **Delivery path:** `from-host\updates\` holding `update-<N>.zip`, `update-<N>.json` (the new signed baseline), `update-<N>.json.sig`. The peer's watcher lists `Get-ChildItem -LiteralPath $InboxDir -File` (watch-inbox.ps1:158, not recursive), so a subfolder is never listed; and at the top level `.zip/.json/.sig` fail `Test-DropName` (.txt/.md only). Proven in TESTS.
5. **Signing:** `ssh-keygen -Y sign -n courier-update` over `update-<N>.json`; the json carries `zip_sha256` and every file hash. `allowed_signers` line `host namespaces="courier-update" <pubkey>`.
6. **update.ps1** order: launch check (plain shells up to **explorer.exe only**: `Test-LaunchAllowed -Mode Watch` plus refusing a svchost/Task-Scheduler root; a consent/mistake guard, NOT a wall against same-user code, see REFUTER C4) and no piped input -> newest `update-<N>.json` -> signature (installed `allowed_signers`) -> signed version == N and > installed version -> zip SHA-256 -> extract to temp -> exact file set + every hash -> apply set = files whose hash changed vs the peer's installed baseline -> STOP with a list if any of those differs on disk from the peer's installed baseline -> changelog + type `yes` -> backup + apply -> canary -> FAIL = roll back.
7. **Rollback:** before apply, copy every file in the apply set that exists (+ `BASELINE.json`) to `Root\update-backup\<stamp>\` and record its hash; files that did not exist are listed. On canary FAIL: copy back, delete the created ones, re-hash and require equality with the pre-update hashes (prints ROLLED BACK or ROLLBACK MISMATCH). *(After the refuter:)* the snapshot is also saved as `snap.json` with a marker `update-in-progress.txt`; if a run dies mid-install (window closed, Ctrl+C), the next `update.ps1` run restores from it first (RESTORED) and doctor shows `update = INTERRUPTED`.
8. **Testability without a bypass flag:** update.ps1 has NO test switch (a flag an AI can pass is a bypass). Every guard is one line tagged `# CHECK:<name>` or `# GATE`; tests run a scratch copy with the tagged line(s) deleted. The real, untouched file is what the AI-ancestor test runs.
9. **Ticket budget (8 KB = 8192 B):** header+route ~300 B, doctor <= 2 KB (lists capped at 12 ids each), seen tail ~400 B, "what I tried" <= 1 KB, LOCAL-CHANGES since the installed baseline's date <= 1.5 KB (last 15 lines), leaves > 2.5 KB spare. LOCAL-CHANGES lines are `date | area | why` with no paths (area from a fixed list), for the same red-flag reason.
